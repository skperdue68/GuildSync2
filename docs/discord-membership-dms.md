# Discord membership DMs

An officer starts an alphabetical campaign for current Discord members without a confirmed ESO account link. The bot waits a random window — 10–15 minutes by default — before its first attempt and between subsequent attempts. The window is a live setting, so it can be shortened or lengthened while a campaign is running. It rechecks eligibility immediately before sending. Recent contacts, existing links, bots, departed members and community preferences are skipped without waiting another interval.

## History

A confirmed membership DM adds a **Membership DM sent** note to that member's Discord history, and every reply adds a **Membership DM response** note naming the chosen option (with the linked ESO account when one was established). A failed or uncertain attempt adds a **Membership DM not delivered** or **Membership DM delivery uncertain** note with Discord's reason, so the member's history shows who did not get a DM and why. Marking or clearing the membership contact preference adds a **Membership DM preference** note, and a reply records whether they supplied an ESO account, are no longer in the ESO guild, no longer play ESO, asked to be removed, or sent another response. Officers see these in **Lookup Member History**. Test messages and test responses are never recorded.

## Configure

In GuildSync, open **Reports & Admin → Administrator Configuration → Discord membership DMs**:

- Enable officer-initiated membership DMs. Enabling alone does not create a campaign.
- Set the minimum days between confirmed membership DMs; the default is 30, configurable from 1 to 365.
- Set the shortest and longest waits between attempts in seconds; defaults are 600 and 900 (10–15 minutes). Saving a faster window shortens a wait already in progress on the next bot poll, without pausing or restarting the campaign.
- In a Discord member's link window, tick **Does not play ESO / not in Alphabet Mafia (stay on Discord)** to stop membership DMs for that Discord member. Ticking it also removes any ESO↔Discord link saved for them, because an unavailable member is not connected; automatic linking will not rebuild that pair while the tick stands. It is skipped by every future campaign, its link dot turns purple in the Discord member list and the Guild Roster, and the same window shows the last DM send, its outcome and the member's latest reply. Clearing the tick allows contact again.
- Running the **Discord Rank Audit** applies that same tick to any member whose linked ESO accounts have all left the roster, and leaves that member out of the report; the tick clears itself once one of those accounts is back on the roster. This mark keeps the ESO↔Discord link, so a returning member is not mistaken for someone who never linked, and it adds a **Membership DM preference** note to that member's Discord history. The mark is applied automatically as soon as a roster sync shows their ESO account gone — running the report is only an extra chance to catch up — and an officer's own preference is never overwritten. Clearing the tick for a departed member keeps it cleared until their account is back on the roster.
- Edit the message using `{name}`, `{guild}` and `{suggested_link}`. The five buttons are added automatically, and so is the closing notice that responses go to guild officers — unless the template already contains that exact sentence, in which case it is not repeated. The default text says the campaign is only updating membership records, that nobody is removed for not being an ESO guild member, for no longer playing ESO or for not being active on the server, that some areas may later be reserved for current guild members, and how to link an account; it ends with a `--{guild} Consigliere` signature. `{suggested_link}` becomes a line naming a possible ESO account match when a fuzzy candidate exists, and nothing at all when there is no suggestion.
- Select a reply destination type (**channel** or **user**) and its numeric Discord ID. A channel must be in this Discord server and writable by the bot; a user must accept the bot’s DMs.
- Optionally choose a numeric community role ID. Blank records preferences without changing roles. A configured role requires the bot’s Manage Roles permission and a role position above it. These responses do not remove existing access or rank roles.

The same settings are documented in the backend `.env.example`. They are backend-owned live settings; they do not require restarting the bot when saved through GuildSync. The bot must have `DISCORD_GUILD_ID` configured and be connected to the same backend.

Deploy the updated bot and backend together. Register the new command with the bot package’s existing `npm run deploy` command when ready to update Discord. Development tests do not register commands or send actual DMs.

## Soldier promotions

The **Promote - Soldier** user context-menu command (right-click a member, then Apps) queues the whole promotion. The role change and the reminder DM are applied together when the queue reaches it, never when the officer clicks, and the queue survives a bot or backend restart. Promotions take priority over campaign entries at the next paced slot, so one is sent before the next membership DM rather than alongside it, and it is independent of the member's campaign eligibility and contact preferences. The officer who queued it receives a DM receipt with the member, the roles removed and added, and the send outcome.

## Officer commands

The commands require the Discord **Consigliere** or **Kingpin** role and an approved GuildSync **User** or **Admin** account. Members without either officer role are refused. The **Discord Reminders** section of GuildSync’s Admin tab applies the same rule: it appears only for an approved User or Admin whose guild rank role is Consigliere or Kingpin.

| Command | Result |
| --- | --- |
| `/membership-dm start` | Refresh the Discord roster and start a new eligible-member campaign. |
| `/membership-dm pause` | Stop new sends; a request already in flight may finish. |
| `/membership-dm resume` | Resume the saved alphabetical queue with a fresh scheduled delay. |
| `/membership-dm restart` | Build a fresh queue, retaining contact dates and preferences. Refuses to replace an active send. |
| `/membership-dm status` | Show state, last attempted name, last successfully sent name, remaining count, uncertain count, which members are uncertain, the ten most recent failed, skipped or uncertain attempts with their reasons and times, and next attempt time. |
| `/membership-dm status user:@someone` | Also show that member’s last confirmed send date, last attempt outcome and reason, and community preference. |
| `/membership-dm resolve user:@someone outcome:delivered\|retry` | Record whether an uncertain DM arrived. `delivered` counts it as a confirmed send; `retry` clears the uncertainty and requeues the member in the current campaign, or makes them eligible for the next one. |
| `/membership-dm repost user:@someone` | Send that member’s latest stored reply again in the current card format, marked with who reposted it. |
| `/membership-dm test user:@someone` | Immediately send a labelled test message to one server member. |

Test messages use the same buttons, forms and forwarding path. Test responses do not establish links, change preferences or roles, or affect ordinary campaign cooldowns or pacing.

## Member responses

1. **I'm in Alphabet Mafia — link my ESO login:** opens a text form for the member's ESO login. A unique active roster account without a confirmed link is linked automatically. Conflicts and officer-blocked pairs go to review without changing existing ownership. A claimed name is self-reported; the modal does not authenticate ownership of an ESO account.
2. **I still play ESO, but I'm not in Alphabet Mafia:** records a persistent community-member preference and stops subsequent membership DMs.
3. **I no longer play ESO — keep me on Discord:** records that preference and stops subsequent membership DMs.
4. **Request removal:** records that the member asked to be removed, marks them **do not contact** so no later campaign messages them, removes any saved ESO↔Discord link, and forwards the request to the officers' reply destination. The bot does not remove the member itself; an officer removes them from Discord.
5. **Other response:** opens a free-text form.

Only the membership DM's buttons and forms produce a forwarded record. A message typed to the bot without pressing one of those buttons is ignored, and a response is accepted only for the exact delivery it answers. Each forwarded record is a Discord embed card. Its author line reads **Membership DM response**, its title is the member's display name (server nickname, then global display name, then username), and its description opens with a bold one-line summary of the answer. Fields carry the server, the Discord name and user ID, the outcome, any community-role failure and, for a repost, who sent it again. When the member typed words, a **Member response** field shows them in a code block; button-only answers omit that field. The embed's left bar is colour-coded: green for a confirmed ESO link, blurple for a saved preference, red for a removal request, amber for an answer awaiting officer review and grey for a test message, and the footer shows GuildSync with the reply's own time. Delivery and response IDs stay in the database rather than the message. A response longer than a field allows is clipped there and attached in full as a text file. Mentions are disabled in forwarded content.

`/membership-dm repost user:@someone` is per use: it sends that member's latest stored reply again in the same card, with `Reposted by <officer>` and the original reply time, to the configured reply destination. The responses table keeps one row per member, so only their most recent reply can be reposted; test replies are never stored.

Buttons remain valid after restarts and validate the intended recipient. Supplying a valid ESO account later clears a previous community preference and removes the optional community role. Existing onboarding promotion behavior handles the confirmed link. A confirmed automatic exact link or an officer's manual link also clears the roster **Does not use Discord** answer and any saved membership preference, and queues removal of the configured community role, so the member reads as connected in the Discord member list and the Guild Roster. The reverse also holds: ticking **Does not use Discord** on the Guild Roster, or either unavailable answer here, removes the member's existing link and keeps auto-linking from restoring it. A pair an officer blocked or unlinked by hand is kept as that officer's decision, and a roster-side removal is recorded in Guild Roster History as **Discord link removed**. Fuzzy candidates never change a preference or a role. A member only counts as managed — and therefore skips the older onboarding reminder — after a confirmed or uncertain membership DM, or after recording a community preference; a failed or skipped send leaves the onboarding reminder available.

## Persistence and failures

Campaign order, send dates, next attempt, preferences, delivery claims, saved test deliveries and reply forwarding state are stored in MariaDB’s `guildsync_membership_dm_state`, scoped by Discord guild. Per-member results live in `guildsync_membership_dm_results` — one row per guild and Discord user holding the display name, last status, reason, delivery and message IDs, last attempt time, last confirmed send time and the uncertain flag — so the guild document no longer grows with every attempt. Send dates and delivery claims embedded by an older version are moved into that table and removed from the document the first time the guild is used. Each member’s latest response is also stored in `guildsync_membership_dm_responses`, one row per guild and Discord user with their display name, confirmed ESO account name, last choice, supplied text and response time; a later response overwrites that row, and `/membership-dm status user:@someone` shows it. Fully forwarded events and settled delivery claims are pruned from the guild state, so it cannot grow with every response. Restarting does not reset cooldowns or cause catch-up bursts. Confirmed send dates require a successful Discord message response; failed DMs are recorded without inventing a successful send.

Closed DMs are recorded as failed and the campaign proceeds at the normal slow pace. Failures before a message is sent — roster or member lookup, eligibility validation or message rendering — are always recorded as failed, never as uncertain. Unknown send outcomes are retained as uncertain rather than automatically sent again. A claim that reports no result within two minutes is also recorded as uncertain with the reason "No delivery result was recorded in time." Both failed and uncertain attempts are written to the member's Discord history with their reason and time; `/membership-dm status` names uncertain members and lists the ten most recent failed, skipped or uncertain attempts with reasons, and after checking the bot log’s delivery/message IDs an officer resolves each one with `/membership-dm resolve user:@someone outcome:delivered` or `outcome:retry`. Platform or worker delays can make sends later than their scheduled time.

Incoming replies are saved locally before submission to the backend. If the backend is unavailable, the bot acknowledges the saved response and replays it idempotently when connected again. Keep the bot’s `data/membership-dm-intake` directory across restarts, or configure an absolute persistent directory with `GUILDSYNC_MEMBERSHIP_DM_SPOOL_DIR` in the bot `.env`. That directory temporarily contains member reply text and is excluded from source control. This protects replies received by a running bot during backend outages; it cannot capture an interaction Discord never delivered to the bot.

Reply forwarding and optional role changes retry independently. A newer membership response supersedes a pending older role change, so an old failed community-role addition cannot undo a later successful link. Fixing the configured destination or role applies to pending retries.

## Smoke test after deployment

Configure a private officer destination, then send a test to your own Discord account. Exercise each button, submit an ESO login and an Other response, and confirm a message typed to the bot without pressing a button is ignored. Confirm the forwarded records are labelled TEST and that actual links, roles, preferences and normal send dates are unchanged. Then start a small real campaign, inspect status, pause/resume it, and verify its next scheduled time and the member’s confirmed send date. No live Discord send or role operation was performed during implementation.
